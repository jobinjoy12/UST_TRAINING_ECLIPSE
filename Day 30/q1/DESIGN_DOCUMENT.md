It does not handle user authentication, product catalog, inventory levels directly, or process payments itself. It owns its data (orders) and provides a clear API for interacting with that data. It communicates with other services only when necessary (e.g., calling Product Service to get product details at the time of order or Payment Service to initiate payment).
*   **Demonstration:** The identified core responsibilities (creation, status management, retrieval of orders) clearly define its bounded context. It doesn't become a catch-all for e-commerce logic. Its autonomy means it can make decisions about its internal implementation and data storage without external dependencies beyond well-defined API contracts with other services.

### c. Decentralized Data Management:

*   **How:** The Order Service has its own dedicated database (as evidenced by `Order.java` entity and `OrderRepository.java` interface, and H2 configuration in `application.properties`). It does not share a database with other services like the Product Service or User Service. It is the sole owner and manager of its order-related data.
*   **Demonstration:** The Order Service's database schema (`orders` table, etc.) is specific to orders and managed exclusively by this service. If the Product Service needs order data (e.g., to show recently purchased items), it must call the Order Service's API. It cannot directly query the Order Service's database. This prevents tight coupling at the data layer, allows each service to choose the most appropriate database technology for its specific needs, and facilitates independent scaling and data model evolution.
